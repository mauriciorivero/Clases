00Panorama

Un proyecto, cuatro formas de traer código

Todo módulo responde a la misma pregunta: ¿cómo uso código que vive en otro archivo? Node.js ofrece cuatro respuestas, y vamos a escribir las cuatro.

Propiorequire()El sistema histórico de Node.js. Síncrono y por defecto.
PropioimportEl estándar oficial de JavaScript. Archivos .mjs.
Incluidofs, path, httpVienen con Node.js. Cero instalación.
De tercerosnpm installCódigo de la comunidad, en node_modules/.

Diagrama: Node.js en el centro conectado a cuatro tipos de módulos — CommonJS, ES Modules, nativos y externos.

01Inicializar

Crea el proyecto con npm init

Terminal
$ mkdir 1_module_vs_common && cd 1_module_vs_common
$ npm init -y
Wrote to .../package.json
package.json
la identidad del proyecto
{
"name": "1_module_vs_common",
"version": "1.0.0",
"main": "index.js",
"type": "commonjs",
"dependencies": {
"is-odd": "^3.0.1"
}
}
  • 1El flag -y acepta todas las respuestas por defecto. Sin él, npm te pregunta una por una.
  • 2La línea clave es "type". Con "commonjs", Node.js lee cada .js como CommonJS. Si fuera "module", los leería como ES Modules.
  • 3Por eso usaremos .mjs para los ES Modules: así conviven los dos sistemas en el mismo proyecto sin pelear.
  • 4dependencies aparecerá sola cuando instalemos el paquete externo en el paso 8.

02Estructura

Una carpeta por sistema de módulos

Terminal
$ mkdir -p src/commonJS src/esModulesJS
$ mkdir -p src/native src/externalModule
estructura del proyecto
1_module_vs_common/
├── package.json
└── src/
├── commonJS/ // require
├── esModulesJS/ // import
├── native/ // fs, path…
└── externalModule/ // npm
  • ·Separar por carpeta no es decoración. Cada una queda como un experimento aislado que puedes ejecutar y romper sin afectar a los demás.
  • ·Dentro de commonJS/ y esModulesJS/ repetiremos a propósito las mismas cuatro funciones matemáticas. Así la única diferencia visible será la sintaxis de los módulos.
  • ·El nombre de la carpeta no cambia nada para Node.js. Lo que decide el comportamiento es la extensión del archivo y el "type" del package.json.

Diagrama: la carpeta src se ramifica en commonJS, esModulesJS, native y externalModule.

03CommonJS · exportar

Publica funciones con module.exports

src/commonJS/math.js
el módulo que ofrece el servicio
function add(a, b) {
return a + b;
}
function divide(a, b) {
if (b === 0) {
throw new Error("Cannot divide by zero");
}
return a / b;
}
module.exports = { add, substract, multiply, divide };

Diagrama: las funciones pasan por module.exports y quedan disponibles para otros archivos.

  • 1Declarar no es exportar. Mientras una función no entre en module.exports, nadie afuera puede verla. Ese es el encapsulamiento del módulo.
  • 2module.exports es un objeto normal. Aquí lo reemplazamos por uno nuevo con las cuatro funciones adentro.
  • 3Siempre al final del archivo. Es la convención: primero se define, después se publica.
  • 4Validar antes de operar. divide lanza un Error si el divisor es cero, en vez de devolver Infinity en silencio.

04CommonJS · importar

Consume el módulo con require()

src/commonJS/main.js
quien consume el servicio
const math = require('./math');
console.log(math.add(5, 3)); // 8
console.log(math.multiply(6, 7)); // 42
console.log(math.divide(20, 5)); // 4
Terminal · desde la raíz del proyecto
$ node src/commonJS/main.js
8
42
4
  • 1'./math' sin extensión. Node.js prueba math.js, luego math.json, luego math/index.js.
  • 2El ./ es obligatorio. Sin él, Node.js buscaría un paquete llamado math en node_modules/, no tu archivo.
  • 3require() devuelve el objeto que el otro archivo puso en module.exports. De ahí el prefijo math. en cada llamada.
  • 4Es síncrono. La línea 1 no termina hasta que math.js se ejecutó completo.

Diagrama: main.js pide math.js con require y recibe de vuelta el objeto exportado.

05ES Modules · exportar

La misma lógica con export

src/esModulesJS/math.mjs
fíjate en la extensión
export function add(x, y) {
return x + y;
}
export function divide(x, y) {
if (y === 0) {
throw new Error("Cannot divide by zero");
}
return x / y;
}

Diagrama: cada función de math.mjs sale marcada individualmente con export.

  • 1No hay línea final. En vez de juntar todo en un objeto, cada función se marca como pública donde se declara.
  • 2La extensión .mjs es la señal. Como el package.json dice "commonjs", esta extensión le avisa a Node.js que este archivo sí es un ES Module.
  • 3Son named exports (exportaciones nombradas). Quien importe tendrá que usar exactamente estos nombres.
  • 4La lógica es idéntica a la de math.js. Lo único que cambió es cómo se publica.

06ES Modules · importar

Trae solo lo que necesitas con import

src/esModulesJS/main.js
aquí la extensión sí va completa
import { add, multiply, divide } from './math.mjs';
console.log(add(5, 3)); // 8
console.log(multiply(6, 7)); // 42
console.log(divide(20, 5)); // 4
Terminal
$ node src/esModulesJS/main.js
8
42
4
  • 1Sin prefijo. Las llaves { } desarman el módulo y traen las funciones directo al archivo: add(5, 3) en vez de math.add(5, 3).
  • 2La extensión .mjs es obligatoria aquí. A diferencia de require(), import no adivina extensiones.
  • 3Importa menos de lo que exportaste. Dejamos substract fuera a propósito: traer solo lo necesario es lo que permite el tree-shaking.
  • 4Mismo resultado, otra sintaxis. Compara esta salida con la del paso 4: idénticas.

Diagrama: main.js importa funciones nombradas desde math.mjs.

07Módulos nativos

Lee un archivo con fs

src/native/native.js
sin npm install
const fs = require('fs');
fs.readFile('./src/native/archivoTexto.txt', 'utf8', (err, data) => {
if (err) {
console.error('Error al leer el archivo:', err);
return;
}
console.log(data);
});
Terminal
$ node src/native/native.js
Este es un archivo de texto de ejemplo…
  • 1require('fs') sin ./ y sin instalar. Node.js revisa primero sus módulos internos, así que fs gana antes de buscar en disco.
  • 2La ruta es relativa a donde ejecutas el comando, no al archivo. Por eso incluye ./src/native/ y debes correrlo desde la raíz.
  • 3'utf8' convierte bytes en texto con tildes y ñ correctas. Sin este argumento recibirías un Buffer.
  • 4El patrón (err, data) es la firma clásica de Node.js: el error siempre va primero y se atiende antes de usar los datos.

Diagrama: main.js llama a fs.readFile, el disco responde y el callback imprime el resultado.

08Módulos externos

Instala un paquete con npm i

Terminal
$ npm i is-odd
added 2 packages in 1s
$ node src/externalModule/main.js
5 es un número impar.
src/externalModule/main.js
const isOdd = require('is-odd');
const number = 5;
if (isOdd(number)) {
console.log(`${number} es un número impar.`);
} else {
console.log(`${number} es un número par.`);
}
  • 1'is-odd' tampoco lleva ./, igual que fs. Pero no es nativo: Node.js lo encuentra en node_modules/.
  • 2added 2 packages, no 1. is-odd depende de is-number. Así crecen los árboles de dependencias.
  • 3No subas node_modules/ a Git. Con package.json y package-lock.json, un npm install lo reconstruye igual.
  • 4Evalúa antes de instalar. Cada paquete es código ajeno ejecutándose en tu proyecto: revisa mantenimiento, descargas y licencia.

Diagrama: npm install descarga is-odd del registro hacia node_modules, y main.js lo requiere desde ahí.

09Comparación

CommonJS frente a ES Modules

Las diferencias que importan

CommonJSES Modules
Importarrequire('./math')import { add } from './math.mjs'
Exportarmodule.exports = { add }export function add()
Extensión.js (o .cjs).mjs (o .js con "type":"module")
CargaSíncrona, en tiempo de ejecuciónAsíncrona, analizada antes de ejecutar
Ruta dinámicaSí: require(variable)Solo con await import(variable)
NavegadorNo funciona sin empaquetadorFunciona nativamente

Diagrama: dos parejas enfrentadas — require con module.exports, e import con export.

  • !No es una competencia. Vas a encontrar los dos en proyectos reales, y necesitas leer ambos con la misma soltura.
  • !No los mezcles en un mismo archivo. import y require() juntos es el error más común al empezar.

10Bajo el capó

Cómo decide Node.js qué cargar

Las tres líneas se escriben casi igual, pero Node.js las resuelve por caminos distintos. Esto explica por qué ./ importa tanto.

tres require, tres caminos
require('fs') // 1 · módulo nativo, viene con Node.js
require('is-odd') // 2 · paquete externo, en node_modules/
require('./math') // 3 · archivo tuyo, ruta relativa

Diagrama: la ruta solicitada pasa por módulos nativos, luego node_modules, y finalmente archivos locales.

  • ·Empieza por los nativos. Por eso no puedes tener un paquete propio llamado fs: nunca ganaría.
  • ·Luego sube carpeta por carpeta buscando un node_modules/, hasta la raíz del disco.
  • ·Con ./ o ../ salta todo eso y va directo al archivo. Es el camino más rápido y predecible.

Lo que quedó claro

  • 1Un módulo es un archivo, y exportar es decidir qué sale de él.
  • 2require/module.exports e import/export resuelven lo mismo, con sintaxis y tiempos distintos.
  • 3Node.js busca primero en lo nativo, después en node_modules/, y solo con ./ va directo a tu archivo.
